# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A Korean-language idle/clicker game ("동물 마을 키우기" — Animal Village Tycoon), built as a static site with no build step, no framework, and no dependencies: `index.html` + `style.css` + `game.js`. Open `index.html` directly in a browser (or serve the folder statically) to run and test it — there is no dev server, package.json, bundler, or test suite.

## Architecture

Everything lives in one flat, layered `game.js` (~2100 lines). When making changes, find the right layer rather than searching randomly:

1. **`CONFIG`** (top of file) — all game balance data: click income/cost curves, stage thresholds, villager roster (15 villagers across 5 themes × 3 tiers), gamble wheel segments/weights, achievements, save-slot count, speed-unlock conditions. This is the single place to retune balance. Extensive Korean comments document past balance passes (each headed "※ 밸런스 N차 재조정") — read the comment above a value before changing it, since most encode a specific bug that was found via simulation (e.g., click-level growth rate, gamble payout expectancy, villager upgrade-vs-hire economics). If you change balance numbers, follow the same pattern: verify with a mental/simulated playthrough, not just formula inspection.
2. **`state`** — the single mutable runtime game state object (money, clickLevel, villager hired/level map, achievements, gamble stats, debtor-mode flag, goalMoney, etc.). `villagerIncomeTimers` is a parallel runtime-only structure (per-villager countdown to next payout) that is intentionally *not* persisted.
3. **Custom data layer** (`CUSTOM_STORAGE_KEY`, `customData`, `getCustomEntry`/`setCustomField`/`getDisplay*`) — user-uploaded overrides (name, emoji, character image, background image, motion, speech-bubble text) per villager, theme, or the main character, stored in `localStorage` separately from save slots so resetting/switching save slots doesn't wipe cosmetic customization. There are no bundled default images anywhere (see Stages below) — a target shows its custom image if uploaded, otherwise an emoji. `"main"` (캐릭터1) and `"main-debtor"` (캐릭터2, the rare gamble persona) are exposed as two separate customization targets in the UI, but both read/write the same `customData.main` entry — `"main-debtor"` fields are transparently remapped to `debtorName`/`debtorEmoji`/`debtorImage`(+`debtorImageStaged`/`debtorImageStage1..N`) inside `getCustomEntry`/`setCustomField` (see `MAIN_DEBTOR_FIELD_MAP`). Character/background images on 캐릭터1/캐릭터2 can optionally vary per game Stage: a `"${field}Staged"` boolean flag (`characterImageStaged`/`backgroundImageStaged`) switches between one fixed image (`${field}`) and per-stage images (`${field}Stage1..MAIN_STAGE_COUNT`) — `resolveStagedField()` picks the right one at render time, and `renderStagedImageField()`/`buildUploadSlotHtml()` render the matching 1-slot or N-slot upload UI in the edit modal. The background image is shared between 캐릭터1 and 캐릭터2 (no separate debtor background) — only 캐릭터1's edit view exposes the background field/toggle. Import/export as JSON is supported (`exportCustomData`/`importCustomData`); the editing UI lives behind a "이미지 커스텀" button that opens a 3-column gallery grid modal grouped into 캐릭터/직원(테마별 소제목)/테마 아이콘 sections (`renderCustomTargetList`/`getCustomGalleryGroups`), which in turn opens the single-target edit modal (`openCustomEditModal`). Image uploads use a custom drag-and-drop dropzone (`.custom-upload-dropzone`), not a bare `<input type="file">`.
4. **`el`** — a single object caching all DOM element references by id, built once at load. Add new lookups here rather than calling `document.getElementById` ad hoc elsewhere.
5. **Derived-value functions** (`getClickIncome`, `getUpgradeCost`, `getStage`, `getVillagerIncome`, `getVillagerInterval`, `getVillagerUpgradeCost`, `getVillagerMaxLevel`, `formatMoneyCompact`, etc.) — pure functions computing display/economy values from `CONFIG` + `state`. Prefer adding a derived function here over storing a computed value in `state`.
6. **Render functions** (`renderMoney`, `renderClickPanel`, `renderStage`, `renderVillagers`, `renderHireThemeContent`, `renderAll`, etc.) — re-read `state`/`CONFIG` and update the DOM. There is no virtual DOM/reactivity: after any state mutation, call the relevant `render*` function (or `renderAll()`) to reflect it. `renderAll()` is called after load/reset/save-restore.
7. **Event handlers** (`handleClick`, `handleUpgrade`, `handleHire`, `handleVillagerUpgrade`, `handleSpin`, `handleSpeedSelect`, `handleSaveSlot`/`handleLoadSlot`, `handleFightChallengeConfirm`, etc.) — mutate `state`, then call the matching render function(s). Wire new interactive elements the same way: handler mutates state → calls render.
8. **`init()`** (bottom of file) — the only entry point; attaches all event listeners and performs first render. Called once at script load (no module system, everything is global scope).

### Key subsystems

- **Save system**: 3 slots (`CONFIG.saveSlotCount`) in `localStorage` under `village-clicker-save-{n}`. `serializeState()`/`applySavedState()` define exactly which `state` fields persist — when adding a new persisted field, update both functions and add a default fallback in `applySavedState` (old saves won't have the field). Cosmetic custom data (`customData`) is *not* part of save slots — it's global across slots/resets.
- **Stages**: the main character progresses through 5 visual "stages" keyed by `clickLevel` crossing `CONFIG.stageThresholds` (`MAIN_STAGE_COUNT` = the count), which only controls the CSS background gradient class (`.stage-bg.stage-N`) — there is no per-stage bundled art. The main character/background image is *only* ever the user's custom upload (`applyStageAssets`/`applyCharacterImageOrEmoji`/`applyBackgroundImageOrFallback`, see staged-image note above); with nothing uploaded it always falls back to an emoji (character) or the stage gradient (background). Same for villagers: `characterImage`/`backgroundImage` are not part of `CONFIG.villagers` at all — emoji or custom upload only.
- **Modals**: every `.modal-overlay` closes both via its own close button and by clicking the dimmed backdrop outside the box (`setupOverlayClickToClose`, wired once per modal in `init()`) — wire new modals the same way. A modal whose body can overflow (currently the gallery grid and the edit modal) keeps the outer `.modal-box` non-scrolling (`overflow:hidden`) and puts an inner `.custom-*-scroll-body` wrapper around the scrollable content instead, so the browser's scrollbar clips to the box's rounded corners rather than poking past them.
- **Debtor mode ("캐릭터2")**: a rare gamble outcome (lowest-weight wheel segment) that swaps the main character's visuals/label into a "debtor" persona; also reachable via a hidden admin tab-sequence (`ADMIN_SEQUENCE`) for testing without relying on gamble RNG.
- **"인생한방" (fight challenge)**: a high-stakes optional event, only available in debtor mode at the final stage — pay an escalating fee for a 50/50 to either clear the debt (`goalMoney`) entirely or double it.
- **Achievements**: declarative — each entry in `CONFIG.achievements` has a `check(state)` predicate; `checkAchievements()` runs these each tick/action and locks in newly-true ones into `state.achievements` (never re-checked once earned).
- **Passive income loop**: `startPassiveIncomeLoop()` drives a `setInterval` tick that advances `villagerIncomeTimers` per hired villager and pays out based on `getVillagerInterval` (which shortens with villager level, floored at `villagerMinInterval`), scaled by the selected game speed (`state.speedLevel`, unlocked via `CONFIG.speeds[].checkUnlocked`).
- **Theme color system**: 8 selectable accent palettes (설정 > 테마 색상), stored separately from `customData`/save slots under `village-clicker-theme-v1` and applied via `document.documentElement.dataset.theme` (`applyThemeColor`/`handleThemeColorSelect` in `game.js`). Each palette overrides `--accent-100/300/600/800/900` *and* `--cream`/`--paper` (page background, nudged warm or cool to match) in `style.css` `:root` + `[data-theme="..."]` blocks; Stage1's background (`.stage-bg.stage-1`) is the only main-character background tied to the theme (`--accent-100/300`) — Stage2–5 keep their own fixed narrative backgrounds. `--berry` (gamble/danger) and `--clay` (warning/upgrade-button) stay fixed regardless of theme. `--accent-600`/`--berry`/`--clay` were picked to be the most saturated tone that still keeps ≥4.5:1 contrast against white button/tab text (WCAG AA) — if retuning these, re-verify contrast (relative-luminance formula, not eyeballing) rather than just picking a color that looks right.

## Conventions

- All in-game text/UI is Korean; keep new UI copy consistent with that.
- No semicolon-free style, no modules, no framework — stay consistent with the existing plain-script, single-file style rather than introducing bundlers/frameworks/TypeScript.
- Money amounts are always integers; the game deliberately avoids fractional payouts (see `villagerIntervalDecay`/`villagerMinInterval` comments in `CONFIG`) — don't introduce non-integer income.
- `init()` calls `setupBasicDeterrents()`, which disables right-click and blocks common devtools/view-source shortcuts. This is a deliberate, known-cosmetic deterrent against casually copying source/images — not real protection (client-side code can never be fully hidden). Don't extend it into something that actually breaks debugging (e.g. `debugger`-loop traps) without the user asking for that specifically.
- Emoji picks matter: emoji added in Unicode 13.0+ (2020, e.g. 🪙, 🦫) render as broken tofu boxes on older OS/font combos even though the browser itself is fine — it's a missing-glyph problem, not fixable by CSS font-family fallback if none of the fallback fonts have that glyph either. Prefer well-established emoji (Unicode ≤9.0/2016, e.g. 🐰🦌🦉🦊🦄) for anything user-facing; where the specific symbol matters and can't be swapped (like the money-popup coin), draw it as inline SVG instead (`MONEY_POPUP_COIN_SVG` in `game.js` is the pattern — plain Unicode text like "₩" inside an `<svg><text>` is safe since it's not an emoji glyph).
- `style.css` has a blanket `.custom-edit-field label { display: block; margin-bottom: 6px; }` rule. Any new `<label>`-based control nested inside `.custom-edit-field` (e.g. the toggle switches, the upload dropzones) needs a *2-class* selector (e.g. `.custom-edit-field-header .custom-edit-toggle`) to win that specificity fight — a bare single-class rule silently loses and the control breaks (drops back to `display:block`).
